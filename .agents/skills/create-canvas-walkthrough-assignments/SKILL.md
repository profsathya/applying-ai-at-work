# Create Canvas Walk-Through Assignments

Turn selected course material into new interactive assignments with optional AI feedback. The reference transformation is [`Brainstorm your list`](../../../course1/sprints/sprint-14/brainstorm-your-list.md) to [`Brainstorm Your List AI-guided activity`](../../../course1/sprints/sprint-15/brainstorm-your-list-ai-guided-activity.md): retain the learning task, turn its directions into a walk-through with participant work and contextual help, and add optional formative AI feedback. Study both artifacts and the rendered new activity before designing a different one. Adapt the structure, prompts, document handling, and feedback to each source; do not copy Brainstorm's content or endpoint.

The [Stakeholder Map local example](../../../examples/walkthroughs/stakeholder-map-local-dry-run.md) demonstrates a source document with tables and an assignment that forbids AI on the first draft. It is a design reference, not a live course item.

Trigger on instructor wording such as “create this as a Canvas walk-through assignment,” “make Sprint 3 Stakeholder Map a Canvas walk-through assignment,” or “create the following assignments as Canvas walk-through assignments.” Accept a Canvas URL, title, module location, or ordinary-language list, with an optional Google Doc, DOCX, ZIP, or other source for each item. Resolve names and linked sources autonomously when possible; do not require the instructor to supply internal IDs or a structured input file.

Each result is a **new module item immediately below its source item** in the same live module. The original remains intact for recovery. Stage the new item unpublished; on an approved release, publish the new item and unpublish the original without deleting it. Treat a named example as a design reference until the instructor requests its conversion.

## Map the source and placement

1. Inspect the live Canvas module and read the source item itself, its linked instructions or assignment, rubric, points, due and availability rules, submission settings, overrides, publication state, submissions, and nearby items. Resolve duplicate titles before drafting. Record the exact module item to follow. Use the read-only `inspect-canvas` workflow where helpful. Do not infer the live module from a storage folder's sprint number.
2. Read any linked or supplied document through [Document Intake](../../../docs/DOCUMENT_INTAKE.md). A Google Doc `/copy` link points to a working template; read the underlying template when access permits. If it cannot be read, ask for an accessible source before adapting its contents. Keep source captures under `.source-intake/` and record provenance beside document-derived Markdown where required.
3. For each requested conversion, record the source item and artifact ID, document, existing participant task, evidence or submission requirement, independence or AI restrictions, assessment settings, and the intended new activity. Flag rubric, availability, override, or other settings the sync layer cannot transfer faithfully. Identify the step at which formative AI feedback can help without doing the participant's work. If the source forbids AI for the whole activity, omit the AI endpoint and buttons. If the new activity would contradict a grading or submission rule, resolve that design question with the instructor. Ask only when a consequential ambiguity cannot be resolved from the available sources.
4. Give the new activity its own title, slug, artifact ID, Markdown file, and Canvas identity. Choose an adjacent position from the **live** module order and preserve the relative order of all existing items. For a page with no assessment settings, use an ungraded replacement only after checking whether a separate linked graded assignment must be preserved; if so, flag the assessment mapping for instructor review. In a batch, keep a source-to-new-item map and account for earlier planned insertions when calculating later positions.

## Design and build the new activity

- Follow [Authoring and Review](../../../docs/AUTHORING.md) and [Authoring Presentation](../../../docs/AUTHORING_PRESENTATION.md). Keep the original learning task and evidence recognizable. Break a long page or document into a coherent sequence of brief teaching, participant action, response capture, contextual help, permitted feedback, and revision. Use `layout: table` for source tables, preserving field rows and evidence columns; the renderer stacks those rows for narrow screens. Include a complete path without AI. Feedback is formative, not an AI grade. Do not invent new points, due dates, rubrics, or completion requirements.
- Use `delivery_mode: guided_assignment`, `presentation: walkthrough`, and `walkthrough_after: <source artifact_id>`. The Brainstorm `interleaved` presentation and `brainstorm-list-v1` feedback contract are specific to that activity. For permitted AI feedback, add reviewed criteria to `services/course-ai/netlify/functions/walkthrough-guidance.mts` keyed by the stable artifact ID, then use the shared `walkthrough-v1` endpoint. Read `services/course-ai/README.md` and Netlify AI Gateway guidance before changing models. The service keeps criteria server-side and sends only the participant response selected for feedback.
- Participants write in the walk-through. Its browser draft is recoverable on that device across activity versions; the assembled response, copy button, and text download let them keep a personal Google Doc or fill the original template. For a file-upload assignment, `export_filename` enables a locally generated Word document that preserves table structure. Keep the original evidence. State exactly what they submit in Canvas. Browser drafts, copying, downloading, and AI feedback do not submit work.
- Keep the Canvas embed free of redundant generic learning-goal or submission panels and links back to the assignment already open. Give participants a path to continue if feedback or clipboard access fails. Preserve accessible labels, keyboard operation, and clear privacy guidance for information sent to the feedback service.

## Review, then publish when authorized

1. Draft new Markdown under the target course's `sprints/` tree; do not edit the source artifact or design documents during staging. Use `publish: false`. Render and serve a local webpage over HTTP, then open it in Codex's right panel as a rendered browser page. Inspect desktop and mobile views, feedback, saved drafts and reload, copy fallback, Word export and contents, and the Canvas submission path. A local feedback sample must be visibly labeled as a preview. Distinguish editorial checks from participant testing.
2. Review substantive text with `reviewing-course-text`. Route through `maintain-homepage` if the course has `homepage.yaml`; an unpublished draft need not gain a public homepage link. Run `canvas_sync/schema.py --artifact` for each new file and the required final validation. Save the authoring review record from `docs/AUTHORING.md`, including source-to-new-item mapping, provenance, preview, and the planned insertion point.
3. If the instructor explicitly requested Canvas draft creation for the exact item in the current turn, stage it unpublished via `sync` and the protected production workflow after validation. Otherwise report the reviewed preview and ask before a Canvas write. Immediately before staging, re-read the live module order and verify each anchor still exists. Verify each new item sits immediately after its source and both visibility states match the draft plan.
4. A later release needs explicit approval for the exact pair or batch. Change the new local artifact to `publish: true` and the original to `publish: false` in one reviewed release. Preflight every pair for submissions and assessment parity. Publish and verify the new item, then unpublish and verify the original. On failure, restore the prior visibility where Canvas permits and stop the batch. Never delete the original. Report the final module order, both publication states, and any pair needing attention. Canvas writes require explicit confirmation in the current turn under `AGENTS.md`.
