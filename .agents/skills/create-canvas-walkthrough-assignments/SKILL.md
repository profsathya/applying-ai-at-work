# Create Canvas Walk-Through Assignments

Turn selected course material into new interactive assignments with optional AI feedback. The reference transformation is [`Brainstorm your list`](../../../course1/sprints/sprint-14/brainstorm-your-list.md) to [`Brainstorm Your List AI-guided activity`](../../../course1/sprints/sprint-15/brainstorm-your-list-ai-guided-activity.md): retain the learning task, turn its directions into a walk-through with participant work and contextual help, and add optional formative AI feedback. Study both artifacts and the rendered new activity before designing a different one. Adapt the structure, prompts, document handling, and feedback to each source; do not copy Brainstorm's content or endpoint.

The [Stakeholder Map local example](../../../examples/walkthroughs/stakeholder-map-local-dry-run.md) demonstrates a source document with tables and an assignment that forbids AI on the first draft. It is a design reference, not a live course item.

Trigger on instructor wording such as “create this as a Canvas walk-through assignment,” “make Sprint 3 Stakeholder Map a Canvas walk-through assignment,” or “create the following assignments as Canvas walk-through assignments.” Accept a Canvas URL, title, module location, or ordinary-language list, with an optional Google Doc, DOCX, ZIP, or other source for each item. Resolve names and linked sources autonomously when possible; do not require the instructor to supply internal IDs or a structured input file.

Each result is a **new module item immediately below its source item** in the same live module. The original remains intact for recovery. Stage the new item unpublished; on an approved release, publish the new item and unpublish the original without deleting it. Treat a named example as a design reference until the instructor requests its conversion.

## Map the source and placement

1. Inspect the live Canvas module and read the source item itself, its linked instructions or assignment, rubric, points, due and availability rules, submission settings, overrides, publication state, submissions, and nearby items. Resolve duplicate titles before drafting. Record the exact module item to follow. Use the read-only `inspect-canvas` workflow where helpful. Do not infer the live module from a storage folder's sprint number.
2. Read any linked or supplied document through [Document Intake](../../../docs/DOCUMENT_INTAKE.md). A Google Doc `/copy` link points to a working template; read the underlying template when access permits. If it cannot be read, ask for an accessible source before adapting its contents. Keep source captures under `.source-intake/` and record provenance beside document-derived Markdown where required.
3. For each requested conversion, record the source item and artifact ID, document, existing participant task, evidence or submission requirement, independence or AI restrictions, assessment settings, and the intended new activity. Flag rubric, availability, override, or other settings the sync layer cannot transfer faithfully. Identify the step at which formative AI feedback can help without doing the participant's work. If the source forbids AI for the whole activity, omit the AI endpoint and buttons. If the new activity would contradict a grading or submission rule, resolve that design question with the instructor. Ask only when a consequential ambiguity cannot be resolved from the available sources.
4. Give the new activity its own title, slug, artifact ID, Markdown file, and Canvas identity. Choose an adjacent position from the **live** module order and preserve the relative order of all existing items. For a page with no assessment settings, use an ungraded replacement only after checking whether a separate linked graded assignment must be preserved; if so, flag the assessment mapping for instructor review. In a batch, keep a source-to-new-item map and account for earlier planned insertions when calculating later positions.

## Design and build the new activity

- Follow [Authoring and Review](../../../docs/AUTHORING.md) and [Authoring Presentation](../../../docs/AUTHORING_PRESENTATION.md). Keep the original learning task and evidence recognizable. Break a long page or document into a coherent sequence of brief teaching, participant action, response capture, contextual help, permitted feedback, and revision. For a rectangular source-document table, use a `kind: table` task; `layout: table` remains the field-per-entry format for existing activities. Include a complete path without AI. Feedback is formative, not an AI grade. Do not invent new points, due dates, rubrics, or completion requirements.
- Use `delivery_mode: guided_assignment`, `presentation: walkthrough`, and `walkthrough_after: <source artifact_id>`. The Brainstorm `interleaved` presentation and `brainstorm-list-v1` feedback contract are specific to that activity. Enable AI feedback on every writable response task by default: configure the shared `walkthrough-v1` endpoint, then add reviewed criteria for the artifact ID and **every writable task ID** to `services/course-ai/netlify/functions/walkthrough-guidance.mts`. Table feedback runs one response row at a time, under its task ID. A read-only table has no AI button. If source restrictions prohibit AI for the whole activity, omit the endpoint and record `feedback_omission_reason`; if a specific writable task must omit AI, set `feedback_enabled: false` and record that task's `feedback_omission_reason`. Do not treat a preview sample as live provider verification. Read `services/course-ai/README.md` and Netlify AI Gateway guidance before changing models. The service keeps criteria server-side and sends only the participant response selected for feedback.
- Participants write in the walk-through where the source calls for a response. Its browser draft is recoverable on that device across activity versions. A table task copies the source grid with any answers as HTML and plain text and provides a selectable table if clipboard access fails. Set `export_filename` on every walk-through containing a table so the same grid can be downloaded as a Word document, including in text-entry assignments. Keep the original evidence and state exactly what participants submit in Canvas. Browser drafts, copying, downloading, and AI feedback do not submit work.
- Every `presentation: walkthrough` uses the shared opening to identify it as a Canvas walk-through assignment, explain the step-by-step activity and browser draft, and point to the bottom submission action. Keep one shared finish section after the activity: text-entry assignments copy completed work for pasting into Canvas's text-entry box; file-upload assignments download a Word document for uploading in Canvas. The Copy button on a file-upload assignment is for records. Read-only-only tables offer a reference copy without claiming there is a response to submit. Check that each route matches the source's actual Canvas submission setting and that participants know copying or downloading alone does not submit work.
- Keep the Canvas embed free of duplicate author-written generic learning-goal or submission panels and links back to the assignment already open. Give participants a path to continue if feedback or clipboard access fails. Preserve accessible labels, keyboard operation, and clear privacy guidance for information sent to the feedback service.

### Map source tables

For a Google Doc or DOCX table, use the selected table block in the private `source-packet.json`, not its flattened Markdown rendering. Record the block ID and choose the `base` or `proposed` text view after reading the original. For an editable table, run `canvas_sync/walkthrough_tables.py --packet ... --block ... --view base|proposed --task-id ... --prompt ... --criterion ... --response-row N` (or `--response-cell ROW:COL` for mixed cells). Coordinates are one-based and include the header row. For a reference table, use `--read-only` instead of criteria or response flags. The helper copies every header, source cell, blank row, and line break; blank cells never become inputs automatically. A cell may keep source text above a participant response. Add optional column width weights only when the source warrants them.

Verify the authored task against the same packet with `--artifact <draft.md> --task-id <id>` and the same response flags or `--read-only`. The comparison checks the grid, source text, response-cell choices, and read-only state. Record the source block, selected view, response-cell decisions or read-only choice, and any adaptation in the authoring review. The source must have one header row and equal column counts without merged cells. A `structural_revision` flag requires inspection of the visible grid and base/proposed text, a recorded decision, and `--reviewed-structure` on both draft and verify commands. Merged or otherwise unsupported tables, and grouped headers, need deliberate adaptation rather than silent flattening. Document page breaks do not split a logical table in the walkthrough.

Render the source grid as one table. Put an optional AI button to the right of each response row and its longer, row-labeled result below the table. A read-only table has no response fields, self-check, or AI buttons. Each request includes the row's labeled cells; the service's criteria stay server-side. Confirm that rich copy pastes as a table into Google Docs when a scratch document is available; otherwise record the paste check as unverified. Check that Word export retains headings, guidance, blank rows, and participant answers. Check the selectable-table fallback in the local hosted preview and later inside Canvas's hosted iframe when release is authorized. Existing non-table tasks keep their current copy behavior.

## Review, then publish when authorized

1. Draft new Markdown under the target course's `sprints/` tree; do not edit the source artifact or design documents during staging. Use `publish: false`. Run `canvas_sync/preview_module.py --manifest <course>/manifests/production.json --sprint <storage-sprint> --output <new-review-directory> --check-browser` with the repository virtualenv, then serve that output over HTTP and open its rendered page in Codex's right panel. Supply the documented Node, Playwright, and browser paths if needed. Inspect desktop and mobile views, every writable task's feedback control, right-side row buttons, feedback below the table, saved drafts and reload, rich copy, selectable fallback, Word export and contents, and the Canvas submission path. Compare all enabled task IDs with the server guidance checkpoints. Run the course AI service tests. A local feedback sample must be visibly labeled as a preview; the checker marks the live AI endpoint unverified. Record the browser results and manual findings; distinguish editorial checks from participant testing.
2. Review substantive text with `reviewing-course-text`. Route through `maintain-homepage` if the course has `homepage.yaml`; an unpublished draft need not gain a public homepage link. Run `canvas_sync/schema.py --artifact` for each new file and the required final validation. Save the authoring review record from `docs/AUTHORING.md`, including source-to-new-item mapping, provenance, preview, and the planned insertion point.
3. If the instructor explicitly requested Canvas draft creation for the exact item in the current turn, stage it unpublished via `sync` and the protected production workflow after validation. Otherwise report the reviewed preview and ask before a Canvas write. Immediately before staging, re-read the live module order and verify each anchor still exists. Verify each new item sits immediately after its source and both visibility states match the draft plan.
4. A later release needs explicit approval for the exact pair or batch. Change the new local artifact to `publish: true` and the original to `publish: false` in one reviewed release. Preflight every pair for submissions and assessment parity. Publish and verify the new item, then unpublish and verify the original. On failure, restore the prior visibility where Canvas permits and stop the batch. Never delete the original. Report the final module order, both publication states, and any pair needing attention. Canvas writes require explicit confirmation in the current turn under `AGENTS.md`.
